## 📣 CONTENT PUBLISHING SYSTEM — COMPLETE FLOW

The most common mistake is creating content randomly. This system ensures that every week you produce a blog post, a video, and social media posts with minimal extra effort — because the content flows naturally from the work you're already doing.

### The Core Principle: "Document, Don't Create"

You don't create separate content from the work. The content **is** the work, documented. While you build, you're simultaneously creating the blog post and the video.

### Weekly Content Calendar

```
Monday    → Start project + start taking raw notes
Tuesday   → Build + annotate hard technical decisions
Wednesday → Build + screenshot/GIF key moments
Thursday  → Build + record screen (raw footage of sessions)
Friday    → Finish project + write blog post draft
Saturday  → Review and publish blog post + edit video
Sunday    → Publish video + distribute on socials + weekly review
```

**Step 1 — During the week: Raw Notes**

Keep a `weekly-notes.md` open while you work. Write in real time:

### 🛠️ PROJECT 3: Custom STL Containers — Vector + HashMap from Scratch

**Full description:**

You'll reimplement `std::vector` and `std::unordered_map` from scratch in C++20, in the pedagogical spirit of 42 School but with modern standards. This isn't an empty academic exercise — it's the most effective way to understand what happens under the hood of every C++ code you write. Your `ft_vector<T>` must implement all methods of the standard equivalent: push_back, emplace_back, insert, erase, resize, reserve, bidirectional iterators, exception safety with strong guarantee on all mutating methods, and C++20 Ranges compatibility. Your `ft_hashmap<K,V>` uses open addressing with Robin Hood hashing (more cache-friendly than chaining), efficient tombstones for deletes, and configurable load factor. For both: zero memory leaks confirmed via Valgrind and AddressSanitizer, benchmarks within 10% of std on core operations, and complete auto-generated Doxygen documentation. The project ends with a Big-O analysis of each operation and memory layout diagrams.

**Tech Stack:** Pure C++20

```cpp
template<typename T, typename Allocator = std::allocator<T>>
class ft_vector {
    // Configurable growth factor (default: 2x)
    // Iterator: random access, bidirectional, C++20 ranges compatible
    // Exception safety: strong guarantee on push_back, insert, emplace
    // Move semantics: move constructor and move assignment
};

template<typename K, typename V, typename Hash = std::hash<K>>
class ft_hashmap {
    // Robin Hood hashing — reduces probe length variance
    // Tombstone deletion — O(1) delete without rehash
    // Max load factor: 0.7 (configurable)
    // Automatic resize when load factor exceeded
```

## WEEK 33: Advanced Distributed Systems — Event Sourcing, CQRS & Sagas

### 🛠️ PROJECT 33: E-commerce Backend with Event Sourcing + Saga Pattern

**Full description:**

You'll build the backend of an e-commerce system using Event Sourcing and the Saga pattern — two of the most important and misunderstood patterns in distributed systems. Event Sourcing means the state of an order is not stored directly; instead, you store the sequence of events that happened (OrderCreated, PaymentConfirmed, OrderShipped, OrderCancelled) and reconstruct the current state by replaying those events — which gives you free auditing, time travel to any point in history, and the ability to add new read models without migrating data. The Outbox Pattern guarantees events are always published even if the message broker momentarily fails — the event is written in the same database transaction and published later. ## WEEK 35: Distributed Database — LSM-Tree Storage Engine

### 🛠️ PROJECT 35: LSM-Tree Storage Engine from Scratch in Go

**Full description:**

You'll build a storage engine based on LSM-Tree (Log-Structured Merge-Tree) — the data structure at the heart of RocksDB, Cassandra, LevelDB, and many other modern database systems. The LSM-Tree is optimized for high-speed writes: instead of writing directly to disk in a random position (which is slow), it writes sequentially to the WAL for durability and to the in-memory MemTable for speed, and periodically flushes to immutable, sorted SSTables on disk. The Write-Ahead Log guarantees no data is lost in a crash — on restart, you replay the WAL to reconstruct the MemTable. SSTables have a Bloom Filter (which you implement from scratch) to avoid unnecessary disk reads on GETs of non-existent keys, and a sparse index for efficient binary search. The compaction process merges L0 SSTables into L1, L2, L3 with sorted runs without overlaps to reduce write amplification. MVCC uses timestamps on each entry so reads see a consistent snapshot without blocking writes. Mandatory benchmarks against BadgerDB (LSM in Go, open-source) show where you stand relative to a mature implementation.

**Tech Stack:** Go + mmap

The Secrets Vault in Rust with AES-256-GCM stores encrypted secrets with RBAC per namespace, audit log with hash chaining, automatic secret rotation, and a CLI + API. Integration between the four: the SIEM detects an attack and automatically instructs the WAF to block the attacking IP.

**Tech Stack:** Go + Python + Rust + PostgreSQL + ClickHouse + Nginx

## The Truth

This roadmap is hardcore by design. 4-6 hours per day, 365 days, without long breaks. If on a given day you can only manage 1 hour, do that hour. Imperfect consistency always beats sporadic perfection.

## When You Want to Quit

It will happen — probably around week 6-8 (the "valley of despair"). What works:

- Return to your why — write it down and read it when motivation drops
- Temporarily switch projects — the variety is intentional
- Share what you're building — the audience creates accountability
- Celebrate the journey — your self from 4 weeks ago would be impressed

## Red Flags

- **Paralyzing perfectionism:** an imperfect published project > a perfect unpublished one
- **Tutorial hell:** 30% theory, 70% practice — never the other way around
- **Isolation:** community accelerates growth more than any resource
